# Project rules — real-time 3D games (TypeScript + three.js)

Applies to every real-time 3D project built from this kit. The target is
**maximum realism** — graphics, materials, physics and feel — at a **locked
frame rate on the target devices**. Read `AGENT.md` first. This file adds to it
and wins where they disagree. `rules/graphics-quality.md` is the graphics
contract and the acceptance checklist; `docs/graphics-playbook.md` explains how
each technique was built and measured.

Target devices: a desktop with a high-end GPU in a Chromium browser with WebGPU,
**and** a mid-range Android phone (the game ships as an APK: a full-screen
WebView serving the bundled build offline, with touch controls). Design the High
preset for the desktop, then make the Low preset hold 60 fps on the phone.

These rules come from three shipped games built to this standard (a military
FPS, a tropical lagoon survival game, a tank game). Every rule that says
"never" cost real time when it was broken.

---

## 0. Reference sheets — look at them before you tune anything

All six live in `reference-sheets/`, generated by
`reference-sheets/_generate_references.py` (regenerate, never guess).

| File | Use it for |
|---|---|
| `pbr-material-reference.png` | base colour / roughness / metalness and extra physical-material parameters for every surface |
| `lighting-reference.png` | sun and sky illuminance in lux, EV100 and pre-exposure, colour temperatures, local lights in candela, tone-map curve, grey ramp |
| `scale-reference.png` | true size of soldier, vehicles, tanks, jets and helicopters on one scale, city grey-box dimensions, eye heights |
| `ballistics-reference.png` | G7-model drop, holdover in mil, time of flight and speed at range |
| `hud-layout-reference.png` | safe zones, centre zone and element placement for the FPS, jet, tank and helicopter HUDs |
| `performance-budget-reference.png` | GPU and CPU frame budgets in ms, High / Low ceilings, the per-game 2 ms slot |

**Rule:** a colour, roughness, light intensity, vehicle size or HUD position
that disagrees with a sheet needs a comment saying why. Extra references you
gather go into `reference-sheets/` with a licence line (CC0 or your own; no
scraped stills, no game or film captures).

## 1. Physical units

- SI everywhere: metres, kilograms, seconds, radians internally (degrees only
  at the UI). One world unit = **one metre**; never rescale a model to "look
  right" — the scale sheet says which of you is wrong.
- `g = 9.81 m/s²`, sea-level air density `1.225 kg/m³`, speed of sound
  `343 m/s` at 20 °C (or from the standard atmosphere for flying games).
- Units live in names: `speedMs`, `altitudeM`, `rateRadS`, `sunIlluminanceLux`,
  `flashIntensityCd`. Directional lights in lux, point and spot lights in candela.
- Never mix a physical value and a "feel" multiplier in one number: keep the
  physical number and apply a named, commented tuning factor.

## 2. Architecture (not negotiable)

1. **`WebGPURenderer`** from `three/webgpu`. It falls back to its own WebGL2
   backend when WebGPU is missing (common in Android WebViews): one code path.
   Never `WebGLRenderer`.
2. **All shaders in TSL** (`three/tsl`) on node materials
   (`MeshStandardNodeMaterial`, `MeshPhysicalNodeMaterial`, `MeshSSSNodeMaterial`,
   `MeshBasicNodeMaterial`, `SpriteNodeMaterial`). Forbidden: `ShaderMaterial`,
   `RawShaderMaterial`, `onBeforeCompile`, `ShaderChunk` patches,
   `EffectComposer`. None of them work with the node renderer.
3. **One post chain** in a single `RenderPipeline` (§4.5).
4. **Reversed depth buffer** (`reversedDepthBuffer: true`) when the near plane is
   under 0.5 m or the far plane beyond 2 km. Read depth back with
   `perspectiveDepthToViewZ` (it knows about reversed depth).
5. **Game logic never imports three.js.** It is plain TypeScript with its own
   small vector maths, stepped at a fixed rate, testable headlessly in Node. A
   render layer reads the game state and writes transforms.
6. **Everything procedural is a valid route**: terrain, buildings, vehicles,
   plants, textures and sounds generated in code (the reference games began
   that way, at ~1–2 MB a build). They later took photographed textures for the
   surfaces the eye rests on and prepared models for vehicles, weapons and
   people, where procedural stand-ins were the weakest part of the picture. If
   you use files, follow §5.5, run every model through the preparation scripts
   in `tools/assets/`, and keep a licence line per file (CC0 or CC BY only).
7. Strict TypeScript, `any` banned, one typed config object for every tunable
   (with units and a source or "tuned by hand" comment).

## 3. Simulation and physics

- **Fixed timestep** (60 Hz unless a brief says otherwise), decoupled from
  rendering; accumulate and interpolate transforms for the visual frame. Never
  feed a variable `deltaTime` to physics. Cap the steps per frame.
- One physics approach for the project: a library (Rapier) **or** a
  hand-written integrator for the specific vehicle — never two libraries. A
  flight model, a rotor model or a tank drive is better written by hand from
  forces and moments than bent out of a generic rigid-body vehicle helper.
- Collision shapes are simple: boxes, capsules, convex hulls, height-field
  queries. Projectiles test the logic's own colliders, never render geometry.
- Real mass, centre of mass and inertia. A tank that pivots like a turret or a
  jet that turns like a car is broken even if it "feels ok".
- Projectiles are integrated per step with drag (the same G7 point-mass model as
  `ballistics-reference.png`), never kinematic tweens or hitscans. The aiming
  solution (lead, holdover, pipper) uses the same integrator.
- Explosions apply impulse with distance falloff and line-of-sight occlusion.
- Deterministic where possible: seeded RNG, fixed step, no `Date.now()` in logic.
- Input goes through a rebindable action layer. Gameplay never reads
  `event.code`.

## 4. Rendering

### 4.1 Light, exposure and colour — before any other lighting work

- Author lights in physical units from `lighting-reference.png` (sun 100 000 lx
  at noon, not "intensity 3"); colours from kelvin.
- **Pre-exposure**: multiply every light, emissive and sky value by
  `exposure = 1 / (1.2 · 2^EV100)` before rendering (Lagarde & de Rousiers 2014).
  Without it the sun's glint overflows FP16 (65 504) and TAA smears black or
  white pixels over the frame.
- **Auto exposure** from a luminance histogram: reduce the HDR frame to a small
  grid on the GPU, read it back **asynchronously and throttled** (every ~6th
  frame — every readback is a sync point on a phone), adapt bright→dark slowly
  (~2 s) and dark→bright fast (~0.5 s), clamp EV per preset.
- Output colour space sRGB. Tone map **once**, in the output stage. ACES Filmic
  by default with an A/B switch to AgX (ACES pushes fire to yellow, afterburners
  to white, skies to cyan); pick per game after side-by-side screenshots and
  write the choice down.
- Do not fix a dark scene by raising ambient. Fix exposure, then light.

### 4.2 Sky, atmosphere, fog

- The sky is physical, never a flat colour or a single static HDRI outdoors.
  Ground-based games may use an analytic or Preetham-style sky calibrated to the
  sheet's sky illuminance; **any game that flies** uses a LUT-based atmosphere
  (Hillaire, EGSR 2020) valid from the ground to the service ceiling.
- **One sky function** draws the dome, lights the environment probe, colours
  the fog and is reflected by water, so horizon, haze and reflections agree.
- **Aerial perspective on every object**: distant things take in-scattered sky
  colour and lose contrast. Height fog is part of the same model
  (`scene.fogNode`), never milky white.
- The environment probe (PMREM) includes a ground hemisphere lit by sun and sky
  (ground bounce). Re-bake it **into the same render target** only when the sun,
  the exposure or the weather changed.

### 4.3 Shadows

- One sun `DirectionalLight` with `CSMShadowNode`: 3–4 cascades on High, 2 on
  Low, split to the real play distance, `fade = true`.
- Soft penumbra from the sun's angular size; contact detail from AO.
- **Only nearby things cast**: far vegetation and distant LODs do not render into
  the cascades (each caster is drawn once per cascade).
- Never toggle `castShadow` and never add or remove a light during play (both
  recompile every material). A fixed light set exists from load; fade
  intensities instead.

### 4.4 Global illumination and reflections

- Outdoors the atmosphere and the probe give the ambient. Interiors get a baked
  sky-visibility factor (or baked probes) that scales indirect light only, so
  rooms are darker than the street while sun through windows stays full.
- Screen-space reflections on High for water and wet surfaces, falling back to
  the probe or the analytic sky, never to black.
- AO and specular occlusion apply to indirect light only, never to the sun.

### 4.5 Post chain, in this order

1. HDR scene pass (half float) with an MRT **velocity** output.
2. GTAO on High — at **full resolution**, before TRAA, with temporal filtering.
3. TRAA on High (needs the velocity buffer; FXAA on Low).
4. Screen-space sun shafts (sky pixels only) on High.
5. Bloom in HDR, driven by physical brightness.
6. Exposure, then tone map and grade, then sRGB — once.
7. Contrast-adaptive sharpening (~0.3) on High to win back what TAA softens.
8. Film grain and chromatic aberration off by default.
9. HUD after everything, **never bloomed**.

Every switch the frame governor or a mode toggles (AO on/off, shaft samples,
thermal view, reflections) is a **uniform**, never a change of the node graph.

### 4.6 Special cases

- Rotor blades: above ~50 % RPM cross-fade to a blurred disc with a moving
  blade-shadow texture, driven by RPM.
- Muzzle flash: a light that always exists, raised for 1–2 frames, no shadow,
  plus an emissive flipbook (candela from the sheet).
- Render-to-texture views (scopes, gunner sights, MFDs, sensor turrets): lower
  resolution than the main view, LOD chosen with their magnification, and a
  line in the per-game budget. Render a second camera only after the main view
  compiled once.

## 5. Materials and textures

### 5.1 Materials

- `MeshStandardNodeMaterial` by default; `MeshPhysicalNodeMaterial` only for
  clearcoat, transmission, sheen or anisotropy.
- Values from `pbr-material-reference.png`. Non-metals: linear luminance
  0.021–0.92. Metals: base colour = F0, never darker than about `#b4b4b4`.
  Metalness 1 only for bare metal; paint, phosphate, rust, rubber are 0.
- Wet surfaces: darker, a little more saturated, smoother, clearcoated — the
  same textures driven by a wetness mask, not a second material.
- Foliage: alpha-tested cards with **coverage-preserving alpha mips**, leaf
  colour in transparent texels, normals not flipped on back faces, thin
  translucency with `MeshSSSNodeMaterial` (High only). Do **not** use
  `alphaToCoverage` without MSAA — three disables the alpha test and the cards
  draw solid.
- Restore `alphaTest` after cloning a node material (r186 loses it).

### 5.2 Texture sets

- Per material: base colour (sRGB), normal (OpenGL convention, green = +Y,
  linear), ORM (R = AO, G = roughness, B = metalness, linear), and where needed
  height, emissive and a thermal mask (linear).
- **At most 16 sampled textures per shader stage** — the WebGPU default and the
  phone limit (software renderers allow more, so headless tests will not catch
  it). Splat terrain layers go into `DataArrayTexture`s: four layers cost three
  bindings, not twelve. Count every `texture()` in a material.
- No pure black and no pure white in a base colour.

### 5.3 Texel density

| Asset | Target |
|---|---|
| First-person weapon and hands | 20–40 px/cm |
| Vehicles, props, walls near the player | ~10 px/cm |
| Terrain base layers | ~5 px/cm plus a detail layer |
| Terrain seen from altitude (flying) | 1–5 m per pixel colour plus procedural detail |

Check the ground at the lowest eye height the game has (prone 0.45 m, a
hover at 2 m), not at standing height.

### 5.4 Killing repetition and flatness

- Detail normals within ~10 m; macro variation (two low-frequency lookups) at
  every distance; stochastic tiling on large tiled surfaces.
- Triplanar mapping on cliffs and rocks; height-blended splatting on terrain.
- Domain-warp tiled animated patterns (wave patches, cloud noise) so their
  period never shows.
- Projected PBR decals per material; wear in masks (edges, cavities, dust on
  top faces, mud low down). A clean vehicle is unfinished.

### 5.5 If you use files

glTF/GLB (Draco or Meshopt), KTX2 textures with mipmaps generated at encode time
(UASTC for normals and hero textures, never ETC1S for normals), coverage-
preserving mips for alpha cards, anisotropic filtering at the device maximum on
grazing surfaces. Models face −Z in their own space; fix orientation in the
asset. Licences in `LICENSES.md`.

## 6. Models, LOD and streaming

- Real silhouettes and proportions — `scale-reference.png` is the check.
- **One `InstancedMesh` per kind of repeated object** (tree species, rock,
  fence), refilled from a grid of cells around the camera — never hundreds of
  per-chunk meshes (each `InstancedMesh` is its own shader build and a draw per
  shadow cascade).
- Trees: full meshes near, light meshes further, **impostors** beyond (8 baked
  views per species blended by angle, one instanced draw for all species), with
  a **dithered** hand-over band using the same per-pixel distance on both sides.
- Small plants sink into the ground over the last metres of their range — no
  popping.
- Grass from individual blades generated in the vertex stage, thinned with
  distance in a low-discrepancy order, rooted exactly on the terrain triangles.
- Large terrain streams in chunks or rings with skirts; heights from erosion-
  shaped noise with real landforms (ridges, valleys, saddles) — masking,
  hull-down play and sniper lines depend on believable relief.
- One height function feeds logic, collision, vegetation placement, water depth
  and the mesh.

## 7. Cameras

- Every vehicle: interior and exterior cameras on one key. Interiors are real
  geometry with a real eye position and FOV (about 60–75° vertical), lit by the
  interior ambient, receiving the sun's cascades.
- First-person weapons and hands receive world shadows; they sit inside the
  player's collision volume so they never poke through walls.
- Exterior: spring arm, damped, collided with terrain.
- Camera shake from physics events, scaled by one global setting.
- Never cut the camera without a reason the player can see.
- **Aiming never turns the camera.** A turret, a gun or a sensor is aimed with a
  cursor the mouse or the right thumb moves over the view; the sight line is
  the ray through that cursor. The camera stays with the vehicle, so fixed
  weapons' cues stay on its axis.
- Cockpit displays: constant output brightness (not exposed with the scene),
  mipmapped, and never coplanar with their bezel (3–4 mm proud), or they
  flicker. From every seat, nothing of the cockpit blocks the centre of view.

## 8. HUD and UI

- Follow `hud-layout-reference.png`: title-safe 90 %, a centre zone 30 % of the
  screen width wide holds **symbols only, no text**. On 21:9 and wider, anchor
  to the centred 16:9 area.
- DOM or a separate orthographic pass, crisp at the device pixel ratio.
- Aircraft symbology is green stroke, vector drawn, collimated: projected into
  the world so the flight-path marker sits on the real velocity vector.
- Every element has a real source; if nothing feeds it, delete it.
- Damage, hit, lock and warning feedback readable in under 200 ms: a shape
  change plus a distinct sound, not only a colour change.
- Show what the flight computer is doing: the power lever's mode (CLIMB / HOLD /
  DESC) by the collective bar, SAS state, laser range.
- A ballistic cue (rockets, bombs) is computed with the **same integrator and
  step** as the real projectile, or cue and hits disagree at grazing angles.
- Symbols behind the camera are culled in view space (`z > −0.5`), not from the
  NDC z of `project()` (wrong with a reversed depth buffer).
- Touch builds: a floating left stick, a drag on the right that looks or aims
  (never flies), buttons for every action, nothing under the thumbs in the
  centre zone.

## 9. Audio

- Positional, with distance falloff and a real speed of sound (a tank round
  arrives before its bang at 1500 m).
- Layer weapons: mechanism, blast, tail, and a distant version by range.
- Engines blend by RPM and load, never by speed alone. Duck on explosions.
- Generated with Web Audio (noise, filters, oscillators) is fine; samples need a
  licence line.
- A delayed one-shot (a far blast heard after the light) starts **silent**: set
  `gain.value = 0` before scheduling the envelope, or `start(at)` the source at
  the event — an `AudioParam` sits at its default of 1 until its first event.

## 10. Smoothness — zero hitches in play

1. **Build every pipeline behind the loading screen, by rendering it.** Reveal
   one object per material/vertex-layout/instancing key (forced visible,
   un-culled, at least one instance), render **one real frame of the full
   pipeline**, restore; each such frame in its own animation frame (the scene
   pass renders at most once per frame). Do **not** call
   `renderer.compileAsync`: it skips hidden and culled objects, compiles for the
   wrong target, and in r186 waits out its whole timeout on WebGPU.
2. Fill instanced meshes (count ≥ 1) before the warm-up frame. Every other
   camera that draws the scene (scope, sight, mirror, sensor) renders one
   warm-up frame too, into a target with the scene pass's formats, MRT and
   sample count, so that it builds no pipelines of its own.
3. Everything that can appear later exists in the scene from load: holstered
   weapons, the first muzzle flash, decals, particles, rain, night lights at
   intensity 0, every alternative view (thermal, scope, MFD).
4. No material, canvas texture or light created mid-game; share materials.
5. No allocation in the frame loop; pool bullets, decals, particles, sounds.
6. Prove it: a pipeline tracer (count `renderer._pipelines` cache growth after
   load) must show **zero new pipelines** through every player action.

## 10b. Loading time — a budget like the frame

Measured with `tools/measure/load.mjs` (stages, pipelines, uploads) and
`profile.mjs` (CPU by function). The number that counts is **gpu idle** — when
the GPU has finished everything loading queued — not the moment the game says
it is ready.

1. Every loading stage logs `[load] <stage>: <seconds> s`, and a total; the pause
   menu shows the total and the longest stages, so a phone reports its own.
2. **Canvases drawn once are made in memory**
   (`getContext('2d', { willReadFrequently: true })`): a GPU-backed canvas is
   read back across contexts when copied into a texture. Not for canvases
   redrawn every frame.
3. **Instanced meshes filled once share their shaders**: under 1024 instances
   three r186 gives each mesh a uniform buffer under its own name, hence its own
   shader builds in every pass; give static meshes room for one matrix past the
   uniform-buffer limit and the matrices come as a shared vertex attribute
   (playbook §8.4, `render/instancing.ts`).
4. **Few materials**: one per kind of surface with switches as uniforms, not one
   per prop. State the pipeline count before and after any change that adds a
   material, an instanced mesh or a camera.
5. **No trigonometry in per-sample load loops** (table-driven gradient noise),
   nothing two systems need computed twice, heavy bakes on workers or the GPU.
6. Ship the APK through a release, not a workflow artifact per run (the storage
   quota fills and the build fails at the upload).

## 11. Performance and measurement — from day one

- **Locked 60 fps**; budget 14 ms GPU, CPU separately. The per-game 2.0 ms slot
  (`performance-budget-reference.png`) is spent on one signature feature.
- Ceilings, High / Low: 2500 / 1500 draw calls, 12 / 4 M triangles,
  120 / 80 materials, 4 / 2 shadow casters (lights), 8 / 2.5 GB textures.
  Over a ceiling, the fix is content.
- **Fixed benchmark spots** (spawn, spawn turned round, the heaviest views):
  a menu button and a `?bench` URL flag; settle ~45 frames, measure ~120; one
  table row per spot: fps, p95 frame time, CPU time, draw calls, triangles, GPU
  ms per pass (timestamp queries through `renderer.inspector`).
- **F3 overlay**: fps, frame ms, governor level, CPU and GPU breakdown, calls,
  triangles, EV, backend.
- **Frame governor**: holds 60 fps by trading image quality, never gameplay —
  first expensive effects (AO, shafts, reflections), then render scale
  100 → 58 % (42 % on phones rendering at 2×); down quickly, up slowly, a step that gains nothing is undone. A
  switch must never recompile.
- Any performance change: the same numbers **before and after** at the same
  spots. "Feels faster" is not a result.
- **Phones render at 2× device pixels** (never capped at 1×) with TRAA and a
  light sharpen on every preset; the frame governor lowers the render scale
  (down to ~0.42) before anything else. A "Fast" preset at 1× is the opt-out.
- Map-scale content is generated, not listed: forests as GPU-instanced impostor
  rings driven by the land-cover texture, terrain as CDLOD from baked grids.
  Heavy bakes run on the GPU (quad passes into render targets) or on worker
  threads in bands, never as one long main-thread loop.
- Gameplay objects (targets, pickups, landing sites) are placed by querying the
  same cover function the renderer uses: never inside a generated wood where
  nobody can see them.

## 12. Code structure

- Entity/system style or plain modules: data and behaviour separated, one fixed
  update order written down in one file.
- Modules under ~400 lines; public API at the top.
- Tunables in one typed config with units.
- Shared engine pieces (perf timer, governor, warm-up, impostors, grass, water
  ripples) are written once and copied file for file between games, fixed at
  the source.

## 12b. Controls (vehicles, aircraft)

Physics stays real; the controls make it flyable. Every rule below came from a
player's complaint.

- **Keys never flip** with an "invert" setting: W is nose down / forward, S nose
  up. Inversion is for a thumb stick only.
- A/D **turn** (mostly yaw in a hover, a coordinated bank with speed); Q/E are
  the pedals (pure yaw).
- Once the game has weapons, **the mouse aims and does not fly**. On touch, the
  right thumb aims and never feeds the flight controls.
- A **flight computer is on by default** (and can be switched off for the bare
  airframe): attitude hold on the stick, heading hold on the pedals with the
  tail rotor fed forward from rotor torque, and **height hold on the power lever
  with a neutral detent** — below it descend, at it hold, above it climb. It
  respects the torque limit, protects against the vortex ring at low speed, and
  flares to a soft touchdown. The touch lever springs back to the detent.
- Fixed weapons fire **along the vehicle's axis**, not carried off by its drift.
- Tilt steering can be switched on in play (and recalibrated), not only in the
  menu.
- Every control behaviour has a unit test in the simulation (hover, climb /
  hold / descend, landing, heading through lever snatches, key mapping). Do not
  judge it from a headless browser: a software renderer runs the simulation at
  a fraction of real time.

## 13. Content and conduct

These are war-themed action games built as entertainment.

- Vehicles, weapons and effects are modelled for **looks and feel**. Never write
  real engineering, weapon-construction, explosive, seeker, jamming or
  targeting-system detail, even in a comment. Public size, speed and silhouette
  numbers are fine — that is what the sheets are for. Radar, sensors and
  missiles are **game abstractions with invented curves**.
- Invented unit names, markings and factions. No real battles, named people or
  atrocities. No real trademarks, logos, liveries or insignia.
- Damage feedback is mechanical: penetration, module hits, smoke, fire, wreck.
  No gore.

## 14. Definition of done for a feature

1. 60 fps on the target devices with the budget respected (numbers in the
   report).
2. Looks right against the PBR, scale and lighting sheets — screenshot next to
   the sheet at noon, golden hour and overcast.
3. Works in interior and exterior cameras, on High and Low, on WebGPU and on
   the WebGL2 fallback, with touch controls.
4. Has sound and failure feedback readable in a second.
5. Tunables in config with units; tests for the logic.
6. Zero new pipelines after load; no console errors.
7. You ran it and looked at it, and you say so in the report.
